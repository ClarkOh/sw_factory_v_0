당신은 테스트 엔지니어입니다. 아래 **유스케이스**로부터 E2E 시나리오 테스트를 작성하세요.

## 이 테스트가 단위 테스트와 무엇이 달라야 하는가

이미 `tests/test_fsm.py` 에 FSM 전이 하나당 테스트 하나가 있습니다. 그것을 반복하지 마세요.
E2E가 잡아야 하는 것은 **전이 하나하나는 맞는데 이어 붙이면 틀리는** 버그입니다:

- 여러 전이를 거친 뒤 누적 상태가 어긋난다 (재고, 잔액, 동전통이 맞지 않는다)
- 유스케이스의 사후조건이 결국 성립하지 않는다
- 예외 경로를 지난 뒤 시스템이 정상 경로로 못 돌아온다

따라서 각 테스트는 **여러 이벤트를 순서대로** 흘려보내고, 마지막에 **업무적으로 관찰 가능한
결과**(배출된 음료, 반환된 금액, 남은 재고)를 단언해야 합니다.
중간 상태 이름만 확인하고 끝나면 단위 테스트와 다를 게 없습니다.

## 세 가지 축을 모두 채워야 합니다

시나리오만 쓰면 한 거래씩만 확인하게 되고, 여러 거래에 걸쳐 조금씩 어긋나는 결함을 놓칩니다.
실제로 그렇게 놓친 적이 있습니다 — 자판기가 코인을 받고 거스름돈을 내주는데
동전 보유량이 전혀 변하지 않았고, 시나리오 테스트 26개가 전부 통과했습니다.
각 테스트가 *한 거래*의 결과만 봤기 때문입니다.

**축 1 — 유스케이스 시나리오** (아래 규칙 3~6)
**축 2 — 불변식** (규칙 7)
**축 3 — 전이 커버리지** (규칙 8)

## 규칙

1. **파일 경로: `{e2e_path}`** — 이 파일만 만듭니다.

2. **기존 테스트(`tests/test_fsm.py`)와 구현 코드를 수정하지 마세요.** 읽기만 합니다.

3. 유스케이스 하나당 최소 하나의 테스트. `main_flow` 를 처음부터 끝까지 재현합니다.
   테스트 이름은 `test_uc01_<짧은설명>` 형식으로, 어느 유스케이스에서 왔는지 드러나게 합니다.

4. **`alt_flows` 도 반드시 테스트합니다.** 실패·예외 경로가 진짜 위험한 곳입니다.
   그리고 예외를 겪은 뒤 **정상 거래가 다시 되는지**까지 확인하세요.

5. 각 테스트 첫 줄 docstring에 어느 유스케이스의 어느 흐름인지 적습니다.
   예: `"""UC-02 주 흐름: 잔액 충분 -> 음료 배출 -> 거스름돈 반환"""`

6. **`acceptance` 항목을 단언으로 옮기세요.** 유스케이스가 "초기화 후 값이 0이다" 라고 했으면
   그것이 그대로 assert가 되어야 합니다.

7. **불변식 테스트**를 별도 섹션으로 넣습니다. 시나리오와 성격이 다릅니다 —
   특정 흐름이 아니라, **어떤 이벤트 열을 흘려도 항상 참이어야 하는 회계 규칙**을 확인합니다.

   - 요구사항 문서에서 “어느 시점에나 ~와 같다” 꼴로 쓰인 항목을 찾아 전부 불변식으로 옮기세요.
   - 그 밖에도 보존 법칙이 성립해야 하는 양을 찾으세요. 예: 초기 재고 == 남은 재고 + 배출 수.
   - **긴 이벤트 열**을 흘린 뒤에 확인해야 의미가 있습니다. 3~4 이벤트로는 어긋남이 드러나지 않습니다.

   이벤트 열은 **고정 시드**로 만듭니다. 외부 라이브러리 없이 `random.Random(42)` 를 쓰세요:

   ```python
   rng = random.Random(42)          # 시드 고정 -> 실패하면 반드시 재현된다
   for _ in range(200):
       ...  rng.choice(...) 로 이벤트와 인자를 고른다
       ...  매 스텝마다, 또는 마지막에 불변식을 단언한다
   ```

   무작위 이벤트에는 **거부되는 것도 섞으세요**(비액면가, 재고 0인 음료, 잘못된 관리자 키).
   정상 경로만 흘리면 불변식이 깨지는 지점을 지나가지 못합니다.
   시드를 2~3개 쓰면 커버리지가 넓어집니다.

8. **전이 커버리지 테스트**를 하나 넣습니다.
   단위 테스트는 전이를 하나씩 고립시켜 확인하지만, *실제 사용 흐름에서 도달 가능한지*는 확인하지 않습니다.
   도달 불가능한 전이가 있다면 FSM이 현실과 어긋난다는 신호입니다.

   구현은 “방금 어느 전이가 발동했는지”를 알려주지 않으므로 **전이 id 단위로는 셀 수 없습니다.**
   대신 `(이벤트 직전 상태, 이벤트)` 쌍 단위로 측정하세요. 명세 표는 공장이 생성해 둔
   `app/_fsm_spec.py` 에 있습니다 — 직접 베껴 쓰지 말고 import 하세요:

   ```python
   from app._fsm_spec import TRANSITIONS
   expected = {(t["src"], t["event"]) for t in TRANSITIONS}
   ```

   이 파일의 다른 테스트들이 흘린 이벤트 + 규칙 7의 무작위 열을 합쳐 실제 실행된 쌍을 모으고,
   빠진 쌍이 있으면 **무엇이 빠졌는지 목록으로** 실패 메시지에 담으세요.

9. 마지막에 **조립된 프로그램이 실제로 실행되는지** 확인하는 테스트를 하나 넣습니다:
   `subprocess` 로 `[sys.executable, "-m", "app", "--script", <임시파일>]` 을 돌려
   returncode == 0 인지 봅니다. 진입점이 깨지면 단위 테스트는 전부 통과해도 프로그램은 안 돕니다.

10. 표준 라이브러리와 pytest만 씁니다. `random` 은 표준 라이브러리이므로 사용 가능합니다.

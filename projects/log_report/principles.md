# 원칙

요구사항보다 위에 있는 것. 요구사항이 바뀌어도 이건 안 바뀐다.
검토와 릴리스 판정은 이 목록을 기준으로 심각도를 정한다.

**P1. 버린 것은 반드시 센다.**
읽었는데 집계에 못 넣은 줄은 개수와 이유가 리포트에 남는다.
조용히 버리면 운영자가 틀린 수치를 맞다고 믿는다. 그게 이 도구의 최악의 실패다.

**P2. 집계 항등식은 항상 성립한다.**
칸별 사건 수의 합 = 집계한 총 사건 수.
칸 안의 수준별 사건 수의 합 = 그 칸의 사건 수.
읽은 줄 수 = 집계한 사건 수 + 버린 줄 수.
어느 한 시점에도 이 등식이 깨진 채로 결과가 나가서는 안 된다.

이 등식들은 기계가 읽는다. 이름은 FSM 의 action 에서 쓰는 것과 같아야 한다.

```보존
등식: read_lines = event_count + dropped
```

**P3. 같은 입력은 같은 출력을 낸다.**
두 번 돌려 다른 리포트가 나오면 어느 쪽도 믿을 수 없다.
실행 시각, 파일 나열 순서, 병렬 처리 순서가 결과를 바꾸면 안 된다.

**P4. 부분 실패가 전체를 죽이지 않는다.**
파일 하나가 깨져도 나머지로 리포트를 낸다. 단 P1에 따라 무엇이 실패했는지 적는다.

**P5. 숫자에는 출처가 붙는다.**
리포트만 보고 어떤 입력에서 나왔는지 알 수 있어야 한다.
출처 없는 숫자는 나중에 아무도 검증할 수 없다.

**P6. 값 없음과 0은 다르다.**
소요시간이 없는 것과 0ms인 것은 다른 사실이다. 섞으면 "빨랐다"로 잘못 읽힌다.

## 심각도

| | 뜻 |
|---|---|
| **high** | 운영자가 **틀린 수치를 맞다고 믿게 된다** (P1·P2·P3 위반), 또는 리포트를 아예 못 만든다 |
| **medium** | 수치는 맞지만 출처·이유를 알 수 없다 (P4·P5 위반), 값 없음과 0을 섞는다 (P6) |
| **low** | 표시·정렬·형식 문제. 수치와 해석에 영향이 없다 |

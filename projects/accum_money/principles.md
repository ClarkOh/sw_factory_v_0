# 원칙 (accum_money)

요구사항보다 위에 있는 것. 요구사항이 바뀌어도 이건 안 바뀐다.
검토와 릴리스 판정은 이 목록을 기준으로 심각도를 정한다.

**심각도 정의**
- `high` = 사용자가 돈을 잃는다, 또는 거래 불능·복구 불능이 된다.
  예: 중복 주문 발생, 포지션 수량을 초과하는 청산 주문, 응답 유실 후 상태 조회 없이 재주문,
  진입 없이 생성된 보호 주문, 저장 안 된 주문 상태, LIVE 모드가 확인 절차 없이 켜짐,
  감사 로그로 명령→결과를 재구성할 수 없음.
- `medium`/`low` = 알려진 이슈로 이월. 다음 버전 요구사항 후보.

**P1. 죽지 않되, 불확실하면 멈춘다.**
장애 하나가 전체를 죽이면 안 된다. 그러나 "죽지 않는다"가 "계속 주문한다"는 아니다.
계정·포지션·주문 결과·시장 데이터·시간 동기화 중 하나라도 확정할 수 없으면
신규 거래를 중단하고 안전 모드로 간다. 안전 모드에서도 조회·재동기화·취소·긴급 정지는 살아 있어야 한다.

**P2. 거래 명령은 트랜잭션이다.**
모든 명령은 `command_id`, 모든 주문은 `client_order_id` 를 가진다.
재시도가 중복 주문을 만들면 안 된다. 응답 유실·타임아웃은 실패가 아니다 —
재주문 전에 반드시 `client_order_id` 로 실제 상태를 조회한다.
전송 전과 후의 상태는 영구 저장소에 기록되고, 로컬과 거래소가 다르면 reconciliation 한다.

**P3. 안전 > 가용성.**
전략이 허용해도 Risk 검사가 거부하면 실행할 수 없다. 검증 실패 주문은 거래소로 나가지 않는다.
수동 명령과 자동 명령은 같은 검증·리스크·감사 경로를 지난다. 우회 경로는 없다.

**P4. 보호 주문은 포지션에 종속된다.**
진입이 성립하지 않았으면 손절·익절 주문이 존재하면 안 된다.
reduce-only 주문 수량이 포지션 수량을 초과하면 안 된다.
포지션이 종료되면 남은 보호 주문은 취소된다.

**P5. 돈 계산은 decimal 로만 한다.**
부동소수점 금액·수량 연산 금지. tick size / step size / 최소 명목금액 보정을 거치지 않은
값은 거래소로 나가지 않는다.

**P6. 기록 없이는 일어나지 않은 것이다.**
명령 원문부터 최종 결과까지 감사 로그만으로 재구성할 수 있어야 한다.
감사 기록은 추가만 하고 수정하지 않는다. API Secret·인증 정보는 어떤 로그에도 남지 않는다.

**P7. 실거래는 명시적으로만.**
기본 모드는 PAPER/TESTNET. LIVE 는 별도 설정 + 명시적 확인 없이 활성화될 수 없다.
현재 모드는 항상 표시된다.
